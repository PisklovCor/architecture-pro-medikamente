# Классификация данных и обоснование необходимости защиты

## Введение

В данном документе представлена классификация данных компании "Медикаменте" по различным параметрам: состоянию данных, уровню чувствительности, профилю риска и другим критериям. Для каждого класса данных приведено обоснование необходимости защиты и требования к уровню защиты.

## Классификация данных по состоянию

Данные в системе могут находиться в трёх основных состояниях: при хранении (at rest), при передаче (in transit) и при обработке (in use). Для каждого состояния требуются свои методы защиты.

### 1. Данные при хранении (Data at Rest)

Это данные, которые хранятся на физических носителях: жёстких дисках, SSD, в базах данных, файловых системах, резервных копиях.

**Примеры:**
- Медицинские карты в формате PDF/JPG на файловом сервере
- Данные пациентов в базе данных PostgreSQL
- Excel-файлы с журналами приёма
- Резервные копии баз данных
- Данные в 1С:Бухгалтерия и 1С:Торговля и склад

**Необходимость защиты:**
- Физический доступ к серверам может привести к краже данных
- Потеря или кража устройств (ноутбуки, внешние диски) с данными
- Несанкционированный доступ к файлам через сеть
- Утечка данных через резервные копии

**Методы защиты:**
- Шифрование дисков (BitLocker, VeraCrypt)
- Шифрование на уровне базы данных (TDE - Transparent Data Encryption)
- Шифрование файлов (EFS - Encrypting File System)
- Шифрование резервных копий
- Контроль физического доступа к серверам

### 2. Данные при передаче (Data in Transit)

Это данные, которые передаются по сети между системами, компонентами, пользователями.

**Примеры:**
- Передача данных между клиентом и сервером (веб-приложение)
- Интеграция с лабораторией анализов через API
- Синхронизация данных между филиалами
- Передача данных в мобильное приложение
- Интеграция ККМ с 1С через TCP/IP
- Почтовые сообщения с персональными данными

**Необходимость защиты:**
- Перехват данных при передаче по сети (man-in-the-middle атаки)
- Утечка данных через незащищённые каналы связи
- Подмена данных при передаче
- Несанкционированный доступ к API

**Методы защиты:**
- TLS/SSL шифрование для всех HTTP/HTTPS соединений
- VPN для удалённого доступа и межсерверного взаимодействия
- mTLS (mutual TLS) для межсервисной коммуникации
- Шифрование почтовых сообщений (S/MIME, PGP)
- Защита API через OAuth 2.0 и API Gateway

### 3. Данные при обработке (Data in Use)

Это данные, которые находятся в оперативной памяти и обрабатываются приложениями.

**Примеры:**
- Данные в памяти веб-приложения при отображении пациенту
- Данные в памяти при генерации отчётов
- Данные в кэше приложений
- Данные в оперативной памяти сервера при обработке запросов

**Необходимость защиты:**
- Дампы памяти могут содержать конфиденциальные данные
- Несанкционированный доступ к памяти процесса
- Утечка данных через логи приложений
- Остаточные данные в памяти после завершения работы

**Методы защиты:**
- Минимизация времени хранения данных в памяти
- Очистка памяти после использования
- Контроль доступа к процессам
- Защита от дампов памяти
- Маскирование данных в логах

## Классификация данных по уровню чувствительности

Уровень чувствительности определяет, насколько критична утечка данных и какие последствия она может повлечь.

### Уровень 1: Критически конфиденциальные данные (TOP_SECRET)

**Характеристики:**
- Прямая угроза жизни и здоровью при утечке
- Нарушение врачебной тайны
- Максимальные штрафы по законодательству
- Критический репутационный ущерб

**Категории данных:**

#### 1.1. Медицинские диагнозы и заключения врачей
- **Описание:** Точные диагнозы, заключения специалистов, медицинские заключения
- **Обоснование защиты:** 
  - Врачебная тайна (ст. 13 ФЗ-323 "Об основах охраны здоровья")
  - Утечка может привести к дискриминации, потере работы, психологическим травмам
  - Максимальные штрафы до 18 млн рублей по 152-ФЗ
- **Требования к защите:**
  - Шифрование AES-256 при хранении
  - TLS 1.3 при передаче
  - Строгий контроль доступа (только лечащие врачи)
  - Детальный аудит всех операций
  - Автоматическое удаление после истечения срока хранения

#### 1.2. Результаты анализов и лабораторных исследований
- **Описание:** Результаты лабораторных анализов, диагностических процедур, медицинские изображения
- **Обоснование защиты:**
  - Содержат информацию о состоянии здоровья
  - Могут раскрыть наличие заболеваний, которые пациент хочет скрыть
  - Утечка может привести к социальной изоляции
- **Требования к защите:**
  - Шифрование AES-256 при хранении
  - Защищённая передача в лабораторию через API с mTLS
  - Контроль доступа на основе ролей
  - Водяные знаки на медицинских изображениях
  - Автоматическое удаление через определённый срок

#### 1.3. Хронические заболевания и история болезни
- **Описание:** Информация о хронических заболеваниях, полная история болезни
- **Обоснование защиты:**
  - Особо чувствительная медицинская информация
  - Может использоваться для дискриминации при трудоустройстве
  - Пожизненная конфиденциальность по закону
- **Требования к защите:**
  - Максимальный уровень шифрования
  - Доступ только для медицинских специалистов
  - Обезличивание при использовании в аналитике
  - Постоянный аудит доступа

### Уровень 2: Высококонфиденциальные данные (RESTRICTED)

**Характеристики:**
- Позволяют идентифицировать личность
- Могут использоваться для мошенничества
- Значительные штрафы при утечке
- Репутационный ущерб

**Категории данных:**

#### 2.1. ФИО и дата рождения
- **Описание:** Полное имя пациента, дата рождения
- **Обоснование защиты:**
  - Прямой идентификатор личности (PII)
  - Требования 152-ФЗ "О персональных данных"
  - Может использоваться для идентификации в других системах
  - Штрафы до 6 млн рублей при утечке
- **Требования к защите:**
  - Шифрование AES-256 при хранении
  - Токенизация при использовании в аналитике
  - Контроль доступа (не все сотрудники должны видеть)
  - Маскирование в интерфейсах для некритичных ролей

#### 2.2. Адрес прописки и место жительства
- **Описание:** Точный адрес прописки, адрес фактического проживания
- **Обоснование защиты:**
  - Позволяет идентифицировать местонахождение человека
  - Может использоваться для преследования, кражи со взломом
  - Требования 152-ФЗ
- **Требования к защите:**
  - Шифрование при хранении
  - Обезличивание (замена на район/город) в аналитике
  - Доступ только для сотрудников ресепшена и бухгалтерии
  - Не передавать в мобильное приложение

#### 2.3. Финансовые данные о платежах
- **Описание:** Информация о платежах, суммах, способах оплаты, данные банковских карт
- **Обоснование защиты:**
  - Может использоваться для финансового мошенничества
  - Требования PCI DSS для данных карт
  - Штрафы до 6 млн рублей
  - Репутационный ущерб при утечке
- **Требования к защите:**
  - Шифрование AES-256 при хранении
  - TLS при передаче
  - Маскирование номеров карт (только последние 4 цифры)
  - Строгий контроль доступа (только кассиры и бухгалтеры)
  - Соответствие PCI DSS
  - Детальный аудит всех операций

#### 2.4. Паспортные данные и документы
- **Описание:** Серия и номер паспорта, данные других документов
- **Обоснование защиты:**
  - Критический идентификатор личности
  - Может использоваться для мошенничества, оформления кредитов
  - Максимальные требования 152-ФЗ
- **Требования к защите:**
  - Максимальное шифрование
  - Хранение только при необходимости
  - Строгий контроль доступа
  - Автоматическое удаление после использования

### Уровень 3: Конфиденциальные данные (CONFIDENTIAL)

**Характеристики:**
- Позволяют связаться с человеком
- Могут использоваться для спама, фишинга
- Средние штрафы при утечке
- Умеренный репутационный ущерб

**Категории данных:**

#### 3.1. Телефон и электронная почта
- **Описание:** Номера телефонов, адреса электронной почты
- **Обоснование защиты:**
  - Позволяют связаться с человеком
  - Могут использоваться для спама, фишинга, мошенничества
  - Требования 152-ФЗ
  - Штрафы до 3 млн рублей
- **Требования к защите:**
  - Шифрование при хранении
  - Маскирование в интерфейсах (только последние цифры/символы)
  - Контроль использования (только авторизованными сотрудниками)
  - Защита от утечки через почту

#### 3.2. Данные о записях на приём
- **Описание:** Информация о записях к специалистам, расписание
- **Обоснование защиты:**
  - Раскрывает информацию о посещениях клиники
  - Может использоваться для преследования
  - Требования 152-ФЗ
- **Требования к защите:**
  - Шифрование при хранении
  - Контроль доступа (ресепшен, врачи, пациент - только свои записи)
  - Аудит изменений записей

#### 3.3. Место работы или учёбы
- **Описание:** Название организации, где работает или учится пациент
- **Обоснование защиты:**
  - Позволяет идентифицировать человека в сочетании с другими данными
  - Может использоваться для социальной инженерии
- **Требования к защите:**
  - Шифрование при хранении
  - Обезличивание в аналитике (замена на категорию)
  - Минимизация данных (собирать только при необходимости)

### Уровень 4: Внутренние данные (INTERNAL)

**Характеристики:**
- Не содержат прямой идентификации
- Могут использоваться для бизнес-аналитики
- Минимальные требования к защите

**Категории данных:**

#### 4.1. Агрегированная статистика
- **Описание:** Статистика по количеству пациентов, услугам, без персональных данных
- **Обоснование защиты:**
  - Может раскрыть бизнес-информацию
  - Минимальные требования
- **Требования к защите:**
  - Базовое шифрование
  - Контроль доступа для внутренних сотрудников

#### 4.2. Общая информация о услугах
- **Описание:** Описание услуг, прайс-листы, общая информация
- **Обоснование защиты:**
  - Коммерческая информация
  - Минимальные требования
- **Требования к защите:**
  - Базовый контроль доступа

## Классификация данных по профилю риска

Профиль риска учитывает вероятность утечки и потенциальный ущерб от неё.

### Высокий риск

**Характеристики:**
- Высокая вероятность утечки (много точек доступа)
- Критический ущерб при утечке
- Требует максимальной защиты

**Примеры:**
- Медицинские карты на общем диске (высокая вероятность доступа многих сотрудников)
- Данные в Excel-файлах (легко скопировать)
- Данные в мобильном приложении (риск потери устройства)
- API интеграция с лабораторией (внешний доступ)

**Меры защиты:**
- Максимальное шифрование
- Строгий контроль доступа
- Детальный мониторинг
- Регулярные проверки безопасности

### Средний риск

**Характеристики:**
- Умеренная вероятность утечки
- Значительный ущерб при утечке
- Требует стандартной защиты

**Примеры:**
- Данные в базе данных (контролируемый доступ)
- Данные в 1С (ограниченный круг пользователей)
- Почтовые сообщения (контролируемая передача)

**Меры защиты:**
- Стандартное шифрование
- Контроль доступа
- Базовый мониторинг

### Низкий риск

**Характеристики:**
- Низкая вероятность утечки
- Минимальный ущерб при утечке
- Требует базовой защиты

**Примеры:**
- Агрегированная статистика
- Общая информация о услугах

**Меры защиты:**
- Базовое шифрование
- Минимальный контроль доступа

## Классификация данных по типу обработки

### Операционные данные (Operational Data)

Данные, используемые в ежедневной работе компании.

**Примеры:**
- Медицинские карты для приёма пациентов
- Записи на приём для ресепшена
- Платежи для кассиров
- ТМЦ для склада

**Требования:**
- Быстрый доступ для авторизованных пользователей
- Шифрование при хранении и передаче
- Контроль доступа на основе ролей
- Аудит операций

### Аналитические данные (Analytical Data)

Данные, используемые для аналитики, отчётов, BI, ML/AI.

**Примеры:**
- Обезличенные данные в Data Lake
- Агрегированная статистика
- Данные для обучения ML-моделей

**Требования:**
- Обезличивание перед использованием
- Шифрование при хранении
- Контроль доступа для аналитиков
- Мониторинг использования

### Архивные данные (Archival Data)

Данные, хранящиеся для долгосрочного хранения или соответствия требованиям.

**Примеры:**
- Архивные медицинские карты
- Старые записи о платежах
- Исторические данные для отчётности

**Требования:**
- Шифрование архивов
- Контроль доступа
- Периодическая проверка целостности
- Автоматическое удаление по истечении срока

## Классификация данных по юридическим требованиям

### Данные, подпадающие под 152-ФЗ "О персональных данных"

**Все персональные данные пациентов и сотрудников:**
- ФИО, дата рождения, паспортные данные
- Адреса, телефоны, email
- Медицинские данные
- Финансовые данные

**Требования:**
- Уведомление Роскомнадзора
- Реестр обработки персональных данных
- Согласие на обработку
- Право на удаление данных
- Техническая и организационная защита

### Данные, подпадающие под врачебную тайну (ст. 13 ФЗ-323)

**Медицинские данные:**
- Диагнозы, результаты анализов
- История болезни
- Медицинские заключения

**Требования:**
- Максимальная защита
- Доступ только для медицинских специалистов
- Пожизненная конфиденциальность
- Штрафы до 5 млн рублей за разглашение

### Данные, подпадающие под PCI DSS

**Финансовые данные:**
- Данные банковских карт
- Информация о платежах

**Требования:**
- Соответствие стандарту PCI DSS
- Шифрование данных карт
- Строгий контроль доступа
- Регулярный аудит

## Выводы

Классификация данных по различным параметрам позволяет:

1. **Определить приоритеты защиты** - какие данные требуют максимальной защиты в первую очередь
2. **Выбрать правильные инструменты** - для каждого класса данных свои методы защиты
3. **Соответствовать законодательству** - выполнение требований 152-ФЗ, врачебной тайны, PCI DSS
4. **Оптимизировать затраты** - не тратить ресурсы на избыточную защиту менее критичных данных
5. **Управлять рисками** - понимать, где наибольшие риски и как их минимизировать

Все данные компании "Медикаменте" требуют защиты, но уровень защиты должен соответствовать их чувствительности, профилю риска и юридическим требованиям.
