# Движок классификации данных перед загрузкой в аналитическое хранилище

## Введение

Данный документ описывает архитектуру и принципы работы движка классификации данных, который обеспечивает автоматическое определение уровня конфиденциальности данных перед их пакетной загрузкой в аналитическое хранилище. Движок является критически важным компонентом системы, обеспечивающим соблюдение принципов Privacy by Design и требований законодательства РФ.

## Проблема

При загрузке данных в аналитическое хранилище возникает несколько проблем:

1. **Структурные изменения данных** - структуры данных на входе могут изменяться (новые поля, изменение типов, переименование колонок)
2. **Отсутствие разметки** - данные не размечены на предмет уровня конфиденциальности
3. **Смешанные данные** - в одном потоке могут быть данные разного уровня конфиденциальности
4. **Необходимость автоматизации** - ручная классификация не масштабируется при росте объёма данных

## Назначение движка классификации

Движок классификации данных решает следующие задачи:

1. **Автоматическое определение уровня конфиденциальности** данных на основе их содержимого и структуры
2. **Адаптация к структурным изменениям** - работа с данными, структура которых может изменяться
3. **Присвоение тегов конфиденциальности** всем данным перед загрузкой в хранилище
4. **Маршрутизация данных** - направление данных в соответствующие слои хранилища в зависимости от уровня конфиденциальности
5. **Валидация данных** - проверка соответствия данных политикам конфиденциальности

## Архитектура движка классификации

### Общая структура

Движок состоит из нескольких компонентов, работающих в пайплайне обработки данных:

```
[Источники данных] 
    ↓
[Приёмник данных] 
    ↓
[Анализатор структуры] 
    ↓
[Классификатор данных] 
    ↓
[Валидатор политик] 
    ↓
[Маршрутизатор данных] 
    ↓
[Хранилище данных]
```

### Компоненты движка

#### 1. Приёмник данных (Data Ingestion Service)

**Назначение:** Приём данных из различных источников для последующей классификации.

**Функциональность:**
- Приём пакетных данных из операционных систем
- Поддержка различных форматов данных (JSON, CSV, Parquet, Avro)
- Обработка потоковых данных (streaming)
- Валидация формата входящих данных
- Обработка ошибок при приёме данных

**Особенности:**
- Асинхронная обработка больших объёмов данных
- Поддержка инкрементальной загрузки (только новые/изменённые данные)
- Очереди для буферизации данных при пиковых нагрузках
- Логирование всех входящих данных

**Технологии:**
- **Apache Kafka** - для потоковой обработки данных
- **Apache NiFi** или **Apache Airflow** - для оркестрации пакетных загрузок
- **Java/Spring Boot** - основной стек компании

#### 2. Анализатор структуры (Schema Analyzer)

**Назначение:** Анализ структуры данных для определения возможных полей с конфиденциальной информацией.

**Функциональность:**
- Автоматическое определение схемы данных (schema discovery)
- Обнаружение новых полей при структурных изменениях
- Определение типов данных (строки, числа, даты)
- Выявление паттернов в именах полей (например, "phone", "email", "fio")
- Сравнение с известными схемами для выявления изменений

**Алгоритм работы:**
1. Сканирование структуры входящих данных
2. Извлечение метаданных (имена полей, типы, примеры значений)
3. Сопоставление с реестром известных схем
4. Выявление новых или изменённых полей
5. Генерация предупреждений при значительных изменениях

**Обработка структурных изменений:**
- **Новые поля** - автоматическое добавление в схему, классификация на основе имени и содержимого
- **Изменение типов** - валидация и предупреждение, если тип изменился критически
- **Переименование полей** - сопоставление старых и новых имён через метаданные
- **Удаление полей** - логирование и обновление схемы

**Технологии:**
- **Apache Avro** или **JSON Schema** - для описания схем
- **Apache Spark** - для анализа больших объёмов данных
- **Собственные алгоритмы** - для сопоставления схем

#### 3. Классификатор данных (Data Classifier)

**Назначение:** Определение уровня конфиденциальности данных на основе их содержимого и метаданных.

**Методы классификации:**

**3.1. Классификация на основе имён полей (Schema-based Classification)**
- Анализ имён полей для определения типа данных
- Использование словаря ключевых слов:
  - "fio", "name", "full_name" → RESTRICTED (ФИО)
  - "phone", "telephone", "mobile" → CONFIDENTIAL (телефон)
  - "email", "e-mail", "mail" → CONFIDENTIAL (email)
  - "diagnosis", "diagnoz" → TOP_SECRET (диагноз)
  - "analysis", "result" → TOP_SECRET (результаты анализов)
  - "address", "adres" → RESTRICTED (адрес)
  - "birth_date", "date_of_birth" → RESTRICTED (дата рождения)
- Поддержка различных языков (русский, английский)
- Учёт контекста (например, "patient_name" более критично, чем "user_name")

**3.2. Классификация на основе содержимого (Content-based Classification)**
- Анализ фактического содержимого полей
- Использование регулярных выражений:
  - Телефоны: `\+7\d{10}` или `8\d{10}`
  - Email: стандартные паттерны email
  - Паспортные данные: серия и номер паспорта
  - ИНН, СНИЛС: соответствующие форматы
- Статистический анализ (например, длина строки, распределение символов)
- Использование ML-моделей для определения типа данных

**3.3. Классификация на основе метаданных (Metadata-based Classification)**
- Использование тегов из операционных систем (если данные уже размечены)
- Анализ источника данных (например, данные из медицинской карты → более высокий уровень)
- Учёт контекста передачи (например, данные для аналитики → требуют обезличивания)

**3.4. Классификация на основе правил (Rule-based Classification)**
- Настраиваемые правила классификации
- Комбинация нескольких факторов (имя поля + содержимое + источник)
- Приоритет правил (более специфичные правила имеют приоритет)
- Поддержка исключений и переопределений

**Уровни конфиденциальности:**

1. **TOP_SECRET** - критически конфиденциальные данные
   - Медицинские диагнозы, результаты анализов, история болезни
   - Требуют максимальной защиты и обезличивания

2. **RESTRICTED** - высококонфиденциальные данные
   - ФИО, дата рождения, адрес, паспортные данные, финансовые данные
   - Требуют строгой защиты

3. **CONFIDENTIAL** - конфиденциальные данные
   - Телефон, email, записи на приём
   - Требуют базовой защиты

4. **INTERNAL** - внутренние данные
   - Агрегированная статистика, общая информация
   - Минимальные требования к защите

**Алгоритм работы классификатора:**

```
1. Для каждого поля в данных:
   a. Проверка имени поля по словарю ключевых слов
   b. Анализ содержимого поля (регулярные выражения, статистика)
   c. Проверка метаданных (теги, источник)
   d. Применение правил классификации
   e. Определение уровня конфиденциальности
   
2. Для всего набора данных:
   a. Определение общего уровня конфиденциальности (максимальный из полей)
   b. Проверка комбинаций полей (квази-идентификаторы)
   c. Присвоение тегов конфиденциальности
   
3. Генерация метаданных классификации:
   a. Уровень конфиденциальности каждого поля
   b. Метод классификации (schema-based, content-based и т.д.)
   c. Уверенность в классификации (confidence score)
   d. Рекомендации по обработке
```

**Технологии:**
- **Apache Spark** - для обработки больших объёмов данных
- **Python/Java** - для алгоритмов классификации
- **ML-модели** - для сложных случаев классификации
- **Регулярные выражения** - для паттернов данных

#### 4. Валидатор политик (Policy Validator)

**Назначение:** Проверка соответствия данных политикам конфиденциальности перед загрузкой в хранилище.

**Функциональность:**
- Проверка наличия необходимых тегов конфиденциальности
- Валидация соответствия данных политикам обработки
- Проверка наличия согласий на обработку (для персональных данных)
- Валидация структуры данных (обязательные поля, форматы)
- Проверка ограничений на передачу данных (например, запрет передачи TOP_SECRET в аналитику без обезличивания)

**Правила валидации:**
- Данные уровня TOP_SECRET не могут попасть в аналитическое хранилище без обезличивания
- Данные уровня RESTRICTED требуют токенизации или обезличивания
- Данные уровня CONFIDENTIAL могут использоваться с маскированием
- Проверка соответствия источника данных политикам передачи

**Обработка ошибок:**
- Блокировка данных, не прошедших валидацию
- Генерация алертов для администраторов
- Логирование всех случаев блокировки
- Возможность ручного переопределения (с аудитом)

**Технологии:**
- **Java/Spring Boot** - основной стек
- **Apache Atlas** - для управления политиками
- **OPA (Open Policy Agent)** - для декларативных политик

#### 5. Маршрутизатор данных (Data Router)

**Назначение:** Направление данных в соответствующие слои хранилища в зависимости от уровня конфиденциальности и результатов классификации.

**Функциональность:**
- Определение целевого слоя хранилища для данных
- Применение правил маршрутизации на основе уровня конфиденциальности
- Обеспечение правильной последовательности обработки (например, обезличивание перед загрузкой)
- Балансировка нагрузки между слоями хранилища

**Правила маршрутизации:**

1. **TOP_SECRET данные:**
   - Обязательное обезличивание перед загрузкой
   - Маршрутизация в слой обезличенных данных
   - Блокировка прямой загрузки в аналитическое хранилище

2. **RESTRICTED данные:**
   - Токенизация или обезличивание
   - Маршрутизация в слой токенизированных данных
   - Возможность загрузки в аналитику после обработки

3. **CONFIDENTIAL данные:**
   - Маскирование при необходимости
   - Маршрутизация в соответствующий слой хранилища

4. **INTERNAL данные:**
   - Прямая загрузка в аналитическое хранилище
   - Минимальная обработка

**Технологии:**
- **Apache Kafka** - для маршрутизации потоков данных
- **Apache NiFi** - для сложной маршрутизации пакетных данных
- **Java/Spring Boot** - для бизнес-логики маршрутизации

## Процесс работы движка

### Этап 1: Приём данных

```
Источник данных → Приёмник данных
- Валидация формата
- Буферизация в очереди
- Логирование приёма
```

### Этап 2: Анализ структуры

```
Приёмник данных → Анализатор структуры
- Определение схемы данных
- Выявление структурных изменений
- Сопоставление с известными схемами
- Генерация метаданных структуры
```

### Этап 3: Классификация

```
Анализатор структуры → Классификатор данных
- Анализ имён полей
- Анализ содержимого
- Применение правил классификации
- Присвоение тегов конфиденциальности
- Генерация метаданных классификации
```

### Этап 4: Валидация

```
Классификатор данных → Валидатор политик
- Проверка соответствия политикам
- Валидация структуры данных
- Проверка согласий на обработку
- Блокировка невалидных данных
```

### Этап 5: Маршрутизация

```
Валидатор политик → Маршрутизатор данных
- Определение целевого слоя
- Применение правил маршрутизации
- Направление данных в хранилище
```

### Этап 6: Загрузка в хранилище

```
Маршрутизатор данных → Хранилище данных
- Загрузка данных в соответствующий слой
- Сохранение метаданных классификации
- Логирование загрузки
```

## Обработка структурных изменений

### Стратегия адаптации

Движок должен адаптироваться к структурным изменениям данных:

1. **Обучение на новых схемах:**
   - Автоматическое обновление словаря ключевых слов при обнаружении новых полей
   - Сохранение истории изменений схем
   - Использование ML для предсказания типа новых полей

2. **Версионирование схем:**
   - Хранение всех версий схем данных
   - Сопоставление старых и новых версий
   - Миграция правил классификации при изменении схем

3. **Ручная настройка:**
   - Интерфейс для ручной настройки правил классификации новых полей
   - Возможность переопределения автоматической классификации
   - Аудит всех ручных изменений

4. **Тестирование:**
   - Автоматическое тестирование классификации на тестовых данных
   - Валидация правил перед применением в продакшене
   - Откат к предыдущим версиям правил при необходимости

## Интеграция с другими компонентами системы

### С Privacy Management Layer:
- Получение политик конфиденциальности для применения правил классификации
- Сохранение результатов классификации в реестре данных
- Обновление политик при изменении требований

### С Data Protection Layer:
- Передача информации об уровне конфиденциальности для применения защиты
- Координация с сервисами обезличивания и токенизации

### С Access Control & Audit Layer:
- Логирование всех операций классификации
- Аудит изменений в правилах классификации
- Контроль доступа к настройкам движка

### С Data Lifecycle Management Layer:
- Применение политик жизненного цикла на основе уровня конфиденциальности
- Управление версиями схем и правил классификации

## Технологический стек

### Основные технологии:
- **Java/Spring Boot** - основной стек компании для сервисов
- **Apache Kafka** - для потоковой обработки данных
- **Apache Spark** - для обработки больших объёмов данных
- **Apache NiFi** или **Apache Airflow** - для оркестрации пакетных загрузок
- **PostgreSQL** - для хранения метаданных и правил классификации
- **Apache Atlas** - для управления метаданными и политиками

### Дополнительные технологии:
- **Python** - для ML-моделей классификации (если потребуется)
- **Elasticsearch** - для поиска и анализа метаданных
- **Redis** - для кэширования правил классификации

## Масштабируемость

Движок спроектирован для масштабирования:

1. **Горизонтальное масштабирование:**
   - Каждый компонент может масштабироваться независимо
   - Использование очередей для распределения нагрузки
   - Параллельная обработка разных батчей данных

2. **Обработка больших объёмов:**
   - Потоковая обработка для реального времени
   - Батчевая обработка для больших объёмов
   - Партиционирование данных для параллельной обработки

3. **Производительность:**
   - Кэширование правил классификации
   - Оптимизация алгоритмов классификации
   - Использование индексов для быстрого поиска

## Мониторинг и метрики

Движок предоставляет метрики для мониторинга:

- Количество обработанных записей
- Время обработки данных
- Точность классификации (если есть эталонные данные)
- Количество ошибок классификации
- Количество заблокированных данных
- Использование ресурсов (CPU, память, сеть)

## Выводы

Движок классификации данных является критически важным компонентом системы, обеспечивающим:

1. **Автоматическую классификацию** данных перед загрузкой в хранилище
2. **Адаптацию к структурным изменениям** данных
3. **Соблюдение принципов Privacy by Design** и требований законодательства
4. **Масштабируемость** при росте объёма данных
5. **Прозрачность** - все операции логируются и аудируются

Движок позволяет автоматически определять уровень конфиденциальности данных и направлять их в соответствующие слои хранилища с применением необходимых мер защиты.
