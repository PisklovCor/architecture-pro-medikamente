# Организация слоёв хранилища данных для конфиденциальных данных

## Введение

Данный документ описывает архитектуру многослойного хранилища данных, специально спроектированного для безопасного хранения и обработки конфиденциальных данных разного уровня. Хранилище обеспечивает изоляцию данных по уровням конфиденциальности и применение соответствующих мер защиты для каждого слоя.

## Проблема

При организации аналитического хранилища данных возникает необходимость:

1. **Хранить данные разного уровня конфиденциальности** - от критически конфиденциальных медицинских данных до внутренней статистики
2. **Применять разные меры защиты** в зависимости от уровня конфиденциальности
3. **Обеспечить изоляцию данных** - данные одного уровня не должны смешиваться с данными другого уровня
4. **Поддерживать аналитику** - данные должны быть доступны для BI/ML/AI систем с соблюдением конфиденциальности
5. **Масштабироваться** - поддерживать рост объёма данных и количества пользователей

## Архитектура многослойного хранилища

### Общая структура

Хранилище организовано в виде нескольких слоёв, каждый из которых предназначен для данных определённого уровня конфиденциальности и применяет соответствующие меры защиты:

```
[Движок классификации данных]
    ↓
[Слой обезличенных данных] ← TOP_SECRET данные после обезличивания
[Слой токенизированных данных] ← RESTRICTED данные после токенизации
[Слой маскированных данных] ← CONFIDENTIAL данные с маскированием
[Слой внутренних данных] ← INTERNAL данные
    ↓
[Слой аналитики] - BI, ML, AI системы
```

## Детальное описание слоёв

### 1. Слой обезличенных данных (Anonymized Data Layer)

**Назначение:** Хранение данных уровня TOP_SECRET после обезличивания для использования в аналитике.

**Характеристики:**
- Данные полностью обезличены - невозможно идентифицировать конкретного человека
- Применены методы k-анонимности, l-разнообразия или дифференциальной приватности
- Удалены все прямые идентификаторы (ФИО, телефон, email)
- Обобщены квази-идентификаторы (точная дата → возрастная группа, точный адрес → район)

**Структура данных:**
- **Raw Zone (Сырые обезличенные данные)** - данные сразу после обезличивания
- **Cleaned Zone (Очищенные обезличенные данные)** - данные после валидации и очистки
- **Curated Zone (Курированные обезличенные данные)** - данные, готовые для аналитики
- **Analytics Zone (Аналитические обезличенные данные)** - агрегированные данные для отчётов

**Меры защиты:**
- Шифрование AES-256 при хранении
- Строгий контроль доступа (только аналитики, без доступа к персональным данным)
- Детальный аудит всех операций
- Теги `ANONYMIZED` для всех данных
- Метаданные о методе обезличивания

**Использование:**
- BI-отчёты на обезличенных данных
- Обучение ML-моделей
- Статистический анализ
- Агрегированная аналитика

**Технологии:**
- **ClickHouse** - для структурированных аналитических данных (уже в стеке)
- **MinIO/S3** - для объектного хранилища (медицинские изображения после обезличивания)
- **PostgreSQL** - для метаданных обезличенных данных

**Пример данных:**
```
До обезличивания:
- ФИО: "Иванов Иван Иванович"
- Дата рождения: "15.03.1985"
- Диагноз: "Сахарный диабет 2 типа"

После обезличивания:
- Возрастная группа: "35-45 лет"
- Пол: "Мужской"
- Диагноз: "Эндокринные заболевания" (обобщённая категория)
```

### 2. Слой токенизированных данных (Tokenized Data Layer)

**Назначение:** Хранение данных уровня RESTRICTED после токенизации для аналитики с возможностью обратного преобразования при необходимости.

**Характеристики:**
- Идентификаторы заменены на токены
- Сохранена связь между записями через токены
- Возможность обратного преобразования только для авторизованных систем
- Таблица соответствий токен-данные хранится отдельно с усиленной защитой

**Структура данных:**
- **Tokenized Data Zone** - данные с токенами вместо идентификаторов
- **Token Mapping Vault** - защищённое хранилище соответствий токен-данные (отдельно, с максимальной защитой)

**Меры защиты:**
- Шифрование AES-256 при хранении
- Токены генерируются криптографически стойким способом
- Таблица соответствий хранится в отдельном, максимально защищённом хранилище
- Доступ к таблице соответствий только для критически важных операций
- Детальный аудит всех операций с токенами
- Ротация токенов при необходимости

**Использование:**
- Аналитика с сохранением связей между записями
- Построение отчётов с агрегацией по токенам
- ML-модели, требующие связей между данными
- Обратное преобразование только при критической необходимости (с аудитом)

**Технологии:**
- **ClickHouse** - для токенизированных данных
- **HashiCorp Vault** - для хранения таблицы соответствий токен-данные
- **PostgreSQL** - для метаданных токенизации

**Пример данных:**
```
До токенизации:
- ID пациента: 12345
- ФИО: "Иванов Иван Иванович"
- Дата рождения: "15.03.1985"

После токенизации:
- Token: "a7f3b2c9d1e4f5g6"
- Возрастная группа: "35-45 лет"
- Пол: "Мужской"

Таблица соответствий (в Vault):
- Token: "a7f3b2c9d1e4f5g6" → ID: 12345 (зашифровано)
```

### 3. Слой маскированных данных (Masked Data Layer)

**Назначение:** Хранение данных уровня CONFIDENTIAL с применением маскирования для снижения риска утечки.

**Характеристики:**
- Данные частично скрыты (маскированы) при отображении
- Полные данные доступны только авторизованным системам
- Разные уровни маскирования в зависимости от роли пользователя
- Сохранена функциональность для аналитики

**Структура данных:**
- **Masked Data Zone** - данные с применённым маскированием
- **Full Data Zone** - полные данные (с усиленной защитой, доступ только для авторизованных систем)

**Меры защиты:**
- Шифрование AES-256 при хранении
- Динамическое маскирование при запросах
- Разные уровни маскирования для разных ролей
- Аудит доступа к полным данным
- Контроль экспорта данных

**Использование:**
- Аналитика с частично скрытыми данными
- Отчёты с маскированными контактами
- BI-дашборды для разных ролей

**Технологии:**
- **PostgreSQL** - с поддержкой динамического маскирования
- **ClickHouse** - для аналитических запросов с маскированием

**Пример данных:**
```
Полные данные:
- Телефон: "+7 912 345 67 89"
- Email: "ivanov@example.com"

Маскированные данные (для аналитики):
- Телефон: "+7 912 *** ** 89"
- Email: "i****v@example.com"
```

### 4. Слой внутренних данных (Internal Data Layer)

**Назначение:** Хранение данных уровня INTERNAL, не содержащих персональных данных.

**Характеристики:**
- Агрегированная статистика
- Общая информация о услугах
- Бизнес-метрики без персональных данных
- Минимальные требования к защите

**Структура данных:**
- **Aggregated Statistics Zone** - агрегированная статистика
- **Business Metrics Zone** - бизнес-метрики
- **Public Information Zone** - общая информация

**Меры защиты:**
- Базовое шифрование при хранении
- Контроль доступа для внутренних сотрудников
- Базовый аудит операций

**Использование:**
- Публичные отчёты
- Бизнес-аналитика
- Дашборды для руководства

**Технологии:**
- **ClickHouse** - для аналитических данных
- **PostgreSQL** - для структурированных данных

**Пример данных:**
```
- Количество пациентов за месяц: 1500
- Популярные услуги: "Консультация терапевта" - 500 обращений
- Средний чек: 2500 рублей
```

## Дополнительные меры защиты

### 1. Изоляция сетей

**Назначение:** Сетевая изоляция слоёв для предотвращения несанкционированного доступа.

**Реализация:**
- Раздельные подсети для каждого слоя
- Firewall правила для контроля трафика между слоями
- VPN для доступа к критическим слоям
- Мониторинг сетевого трафика

### 2. Контроль доступа на основе ролей

**Назначение:** Строгий контроль доступа к каждому слою на основе ролей пользователей.

**Роли:**
- **Data Analyst** - доступ только к обезличенным данным
- **Senior Data Analyst** - доступ к токенизированным данным
- **Security Officer** - доступ к таблице соответствий токен-данные (только для аудита)
- **System Administrator** - технический доступ (без доступа к данным)

**Реализация:**
- RBAC через Keycloak
- ABAC для сложных правил доступа
- Аудит всех операций доступа

### 3. Шифрование данных

**Назначение:** Защита данных при хранении на всех слоях.

**Реализация:**
- **TDE (Transparent Data Encryption)** для баз данных
- **AES-256** для всех данных
- **HashiCorp Vault** для управления ключами
- Ротация ключей шифрования

### 4. Аудит и мониторинг

**Назначение:** Полная прозрачность всех операций с данными.

**Реализация:**
- Детальное логирование всех операций
- Невозможность удаления или изменения логов аудита
- Интеграция с SIEM-системами
- Автоматическое обнаружение аномалий
- Регулярные отчёты о доступе к данным

### 5. Резервное копирование

**Назначение:** Защита от потери данных.

**Реализация:**
- Регулярное резервное копирование всех слоёв
- Шифрование резервных копий
- Хранение копий в отдельном, защищённом хранилище
- Тестирование восстановления из резервных копий

### 6. Управление жизненным циклом данных

**Назначение:** Автоматическое применение политик хранения и удаления данных.

**Реализация:**
- Автоматическое удаление данных по истечении срока хранения
- Архивирование старых данных
- Применение политик на основе уровня конфиденциальности
- Уведомления перед удалением критических данных

## Процесс загрузки данных в слои

### Шаг 1: Классификация данных

```
Данные → Движок классификации
- Определение уровня конфиденциальности
- Присвоение тегов
```

### Шаг 2: Обработка данных

```
Движок классификации → Обработка данных
- TOP_SECRET → Обезличивание
- RESTRICTED → Токенизация
- CONFIDENTIAL → Маскирование
- INTERNAL → Прямая загрузка
```

### Шаг 3: Валидация

```
Обработка данных → Валидация
- Проверка качества обработки
- Валидация соответствия политикам
- Проверка метаданных
```

### Шаг 4: Загрузка в слой

```
Валидация → Соответствующий слой хранилища
- Загрузка данных
- Сохранение метаданных
- Логирование операции
```

## Интеграция с аналитическими системами

### BI-системы

**Доступ:**
- Только к обезличенным и токенизированным данным
- Маскированные данные для некритичных ролей
- Агрегированные данные для публичных отчётов

**Ограничения:**
- Нет доступа к полным персональным данным
- Нет возможности деанонимизации
- Все запросы логируются

### ML/AI системы

**Доступ:**
- Обезличенные данные для обучения моделей
- Токенизированные данные для моделей, требующих связей
- Синтетические данные для некоторых задач

**Ограничения:**
- Нет доступа к реальным персональным данным
- Модели обучаются только на обезличенных данных
- Все операции с данными аудируются

### Системы отчётности

**Доступ:**
- Агрегированные данные для отчётов
- Маскированные данные при необходимости
- Обезличенные данные для статистики

**Ограничения:**
- Нет персональных данных в отчётах
- Автоматическая проверка отчётов на конфиденциальность
- Контроль экспорта отчётов

## Масштабируемость слоёв

### Горизонтальное масштабирование

Каждый слой может масштабироваться независимо:

- **Партиционирование данных** - разделение по времени, категориям, источникам
- **Шардирование** - распределение данных по нескольким узлам
- **Репликация** - для повышения доступности и производительности чтения

### Вертикальное масштабирование

- Увеличение ресурсов для критических слоёв
- Оптимизация запросов для каждого слоя
- Кэширование часто используемых данных

### Производительность

- Индексы для быстрого поиска
- Материализованные представления для агрегаций
- Кэширование результатов запросов
- Оптимизация структуры данных для аналитики

## Мониторинг и метрики

### Метрики по слоям

- Объём данных в каждом слое
- Количество запросов к каждому слою
- Время отклика на запросы
- Использование ресурсов (CPU, память, диск)
- Количество ошибок доступа

### Метрики безопасности

- Количество попыток несанкционированного доступа
- Количество операций с данными
- Время обработки данных
- Качество обезличивания/токенизации

## Выводы

Многослойная архитектура хранилища данных обеспечивает:

1. **Изоляцию данных** по уровням конфиденциальности
2. **Применение соответствующих мер защиты** для каждого слоя
3. **Безопасную аналитику** - работа только с обработанными данными
4. **Масштабируемость** - независимое масштабирование слоёв
5. **Соответствие законодательству** - соблюдение требований 152-ФЗ и врачебной тайны
6. **Прозрачность** - полный аудит всех операций

Такая архитектура позволяет безопасно хранить и использовать конфиденциальные данные для аналитики, не нарушая конфиденциальность пациентов и сотрудников.
